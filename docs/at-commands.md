# 時刻関連の AT コマンド

出典: 3GPP TS 27.007、Fibocom L860 AT Commands User Manual §5.1 (+CCLK p.63-65、+CTZU p.65-66、+CTZR p.67-68)。
マニュアルは転載禁止のため、ここでは形式を要約しています。

## 送るコマンド

| コマンド | 用途 |
|---|---|
| `AT+CTZR=3` | タイムゾーン変更と UTC の通知 `+CTZEU` を有効にする。ltentp が起動時に毎回送る |
| `AT+CCLK?` | モデムの時計を読む。`--cclk-interval` 指定時に、秒の切り替わりを求めるため短い間隔で続けて送る |
| `AT+CTZU=1` | NITZ でモデムの時計を自動更新する (既定値。ltentp は変更しない) |

マニュアルによると、`AT+CTZR=3` はファームウェアのビルド設定によっては使えません。

## 応答の形式

| 行 | 形式 | ltentp での扱い |
|---|---|---|
| `+CTZEU: <tz>,<dst>[,<utime>]` | `<utime>` は UTC で `"YYYY/MM/DD,hh:mm:ss"` | UTC として chrony に送る |
| `+CTZE: <tz>,<dst>[,<time>]` | `<time>` は現地時刻 | 記録のみ (時刻は変換しない) |
| `+CTZV: <tz>` | タイムゾーンのみ | 記録のみ |
| `+CCLK: "<time>±zz"` | `<time>` は `yy/MM/dd,hh:mm:ss` の現地時刻 | 記録のみ。時刻欄からゾーンを引いて UTC にする。ゾーンがなければ UTC とみなす |

- `<tz>` は 15 分単位の整数で、範囲は −48〜+56 です。引用符付き (`"+36"`) と引用符なし (`+36`) のどちらも受け付けます
- `<dst>` は 0〜2 (夏時間の補正の時間数) です
- 時刻の中にカンマがあるので、フィールドは引用符の外のカンマだけで区切ります
- 年は 2 桁 (20yy とみなす) と 4 桁のどちらも受け付けます。マニュアルの `<utime>` の例は 4 桁、実機の `+CCLK` は 2 桁でした
- `<utime>` が省略された、または空の `+CTZEU` も受け付けます (chrony には送りません)

実機では `+CTZEU` がまだ一度も届いておらず、形式は確認できていません (下記)。解析に失敗した行も `PARSE_ERROR` として生の行を記録します。

## 実機で観測したこと (2026-11-17、Windows の MBIM AT トンネル経由)

| コマンド | 応答 |
|---|---|
| `AT+CGMR` | `18601.5001.00.01.17.30` |
| `AT+CTZR=?` | `+CTZR: (0-3)` (3 に対応) |
| `AT+CTZR?` | `+CTZR: 0` |
| `AT+CTZU?` | `+CTZU: 1` |
| `AT+CCLK?` | `+CCLK: "26/11/17,08:51:24+36"` (このときの PC の UTC は 08:51:24.5) |

`+CCLK` の時刻欄は JST (17:51) ではなく UTC と一致し、タイムゾーン欄は +36 (+9 時間) でした。TS 27.007 ではこの欄は現地時刻のはずです。
下の Linux での観測では現地時刻だったため、ltentp は TS 27.007 どおりに扱います。Windows で食い違った原因 (Windows が MBIM 経由でモデムの時計を設定した、など) は確認していません。

## 実機で観測したこと (2026-11-18、Debian 13 + iosm、IIJmio の SIM)

### 起動から登録まで

| 状態・操作 | 結果 |
|---|---|
| 起動直後 | `+CFUN: 4,0` (MBIM でも software radio off)、`+COPS: 2` (登録解除)、`+CTZR: 0`、`+CCLK: "70/01/01,01:03:22+00"` |
| `AT+CPIN?` | `CFUN=4` では `ERROR`、`CFUN=1` では `+CPIN: READY` |
| FCC unlock 前の `AT+CFUN=1` | `OK` を返すが `+CFUN: 4` のまま |
| FCC unlock | ModemManager 上流の `data/dispatcher-fcc-unlock/8086:7560` の Lenovo 方式 (`AT+GTFCCLOCKGEN`/`VER`/`MODEUNLOCK`、SMBIOS type 133 から求めたハッシュ) で成功 |
| unlock 後の `AT+CFUN=1` | `+CFUN: 1,0` になるが、`+COPS: 2` のままで網を探さない |
| `AT+COPS=0` | 約 1 秒で `+COPS: 0,0,"KDDI",7` (LTE)、`+CEREG: 0,1` |

これらは再起動のたびに必要です。ltentp は `AT+CFUN`・`AT+COPS` を送らないので、外で済ませておきます。

### AT ポート

- `/dev/wwan0at0`・`/dev/wwan0at1` とも応答します。Windows の AT トンネルで起きた「最初の応答が返らない」問題は起きません
- 1 つのポートを複数のプロセスで同時に開けます。応答はどれか 1 つの読み手にしか渡らないので、ltentp が使うポートで別のプロセスから AT を送ってはいけません
- `AT+CEREG=2` の URC は at0 と at1 の両方に同時に届きました。URC は `AT+CTZR` などを設定したポートに限らず届くようです

### 時刻

- **`+CTZEU` は届きませんでした。** 両方のポートで `AT+CTZR=3` を設定した状態で、モデムの時計が `70/01/01 +00` から網時刻 `+36` に変わった最初の登録でも (再起動して 2 回確認)、その後 1 時間の間も、登録をやり直したときも出ていません。`+CEREG` の URC は同じポートに届いているので、URC が落ちているわけではありません
- **`+CTZV` (`AT+CTZR=1`) と `+CTZE` (`AT+CTZR=2`) も届きませんでした** (3 回目の再起動後の最初の登録で、at0 を 1、at1 を 2 にして確認)。`AT+CTZR` はポートごとの設定です (片方を変えてももう片方は変わらない)
- 網の時刻は登録の手続きの中で届きます。3 回目の最初の登録では、時計が `70/01/01` から網時刻に変わったのは 14:24:06.855〜.867 の間で、`+CEREG: 1` の通知 (.890) より約 25 ms 前でした
- `+CCLK` は登録の直後に網時刻になりました。時刻欄は現地時刻 (`26/11/18,10:10:19+36` のとき UTC は 01:10:19) です
- `AT+CCLK?` の応答時間は 1.6〜5.8 ms (10 ms 間隔で続けて送ったときの中央値 4.5 ms)
- 秒の切り替わりは ±6〜8 ms の幅で求まり、同じ設定のままなら 1 秒ごとの値のばらつき (標準偏差) は約 3 ms です
- 秒の切り替わりのずれ (モデム − システム) は、時点によって大きく違いました。仕組みは分かっていません:

  | 時点 | ずれ |
  |---|---|
  | 1 回目の起動。最初の登録 (10:09) から約 65 分、登録のやり直し (10:15) から約 60 分後 | +10.5 ms (60 回の平均) |
  | 再起動直後、網の時刻が入る前 (時計は 1970 年から) | −0.5614 s 相当の位置 (66 回) |
  | 最初の登録 (11:43:27) で網時刻になってから 3 分以内 | −0.5618 s (位置は変わらず、秒の数だけ変わった) |
  | `CFUN=4` → `CFUN=1` と `COPS=0` で登録し直した (11:47:40) 後 | −0.815 s (位置が変わり、その後 72 分間、10 分ごとの平均が −0.814〜−0.817 s で一定) |
  | 3 回目の起動、最初の登録 (14:24:06) で網時刻になった後 | −0.724 s (合わせる前の位置 −0.468 から変わった) |

  網時刻は秒単位でしか入っていないように見えます。登録から 72 分たっても UTC に寄っていかなかったので、1 回目の +10.5 ms は時間がたって合わせ直された結果ではありません。なぜ 1 回目だけ UTC に近かったのかは分かりません
- `AT+XSIB16INFO` (`=?` は `(0,1)`) と `AT+XSIB8INFO` がファームウェアのコマンド一覧 (`AT+CLAC`) にありますが、マニュアルにはありません。両方のポートで `=1` にして最初の登録を 2 回、セルの切り替わりを何度か待っても通知は来ませんでした。`?` はいつも `+CME ERROR: not found` です。この網 (KDDI、EARFCN 100 = Band 1) のセルが SIB16 を流していない可能性が高いと考えています (未検証。確かめるにはモデムのトレースが要る)
- MBIM の `--ms-query-nitz` は `+CCLK` と同じ時計を返します (秒単位、同じ遅れ)
- 登録の操作中に別の AT を同じポートに送ると、実行中のコマンドは中断されます (`AT+COPS=0` が 60 秒返らなかったとき、次の `AT+CCLK?` で `+CME ERROR: Command aborted by user`)。時間のかかる操作は ltentp と別のポートで送ります
- 再起動直後は `CFUN=1` にしても SIM が `SIM NOT INSERTED` / `not-initialized` のままのことがありました (2 回とも)。その間に送った `AT+COPS=0` は返らず、別の AT で中断されたあと、数秒〜40 秒で SIM の準備ができて自動で登録しました。`CFUN=4` → `CFUN=1` では数秒で `+CPIN: READY` になります。`CFUN=4` を通すと `+COPS: 2` に戻るので、登録には `AT+COPS=0` が要ります

### モデムのトレース

- iosm には、モデムのトレース用チャネルを debugfs に出す機能があります。`/sys/kernel/debug/wwan/wwan0/iosm/trace_ctrl` に `1` を書くと開き、`trace0` から読みます (止めるときは `0`)
- セキュアブートが有効だとカーネルが `integrity` ロックダウンになり、これらは `Operation not permitted` になります。2026-11-18 にセキュアブートを無効にして使えるようになりました
- 既定の設定 (`AT+XSYSTRACE=10` で一覧。`bb_sw`・`sig_mon`・`lte_l1_sw` などは `Oct`) のままで、何もしなくても約 1 MB/s 流れます。中身は Intel 独自の形式で、printf の書式文字列 (`%d` 入り) やモデム内の関数名が文字列のまま含まれます。引数は文字列になっていないので、値は読めません

登録し直しながらトレースを取って分かったこと (2026-11-18、4 回):

- **NITZ は網から届いています。** 登録のたびに `UL4UtaMsNetNitzInfoIndCb` (NITZ の受信処理) が動き、`Nitz being stored to NVM, mcc:440,mnc: 51` が出ます。タイムゾーンは `variance =<540>` (+9 時間) と読まれています
- **AT の通知は作られかけて、ポートに届きません。** `uta_cat_send_CTZ_unsolicited: enter` がポートごとに 11〜12 回、`URC Type : +CTZV >< SIM ID : 0>< count of processors : 15` が 1 回出ます。同じ書式で出る `+CEREG` は at0・at1 に届くのに、`+CTZV`・`+CTZE`・`+CTZEU` は `AT+CTZR` を 1・2・3 のどれにしても届きませんでした
- そのたびに `C-AT_DBG_WARN : DayLightSaving time not available, val present= 0` が出ます。網の NITZ に夏時間の情報がなく、それが原因で通知を捨てている可能性があります (推測。ソースがないので確かめられない)
- ポートごとの設定を読むログ `CTZUmode_val=<1>CTZRmode_val<n>` は大半が `<0>` で、`AT+CTZR=3` にした at0 の分と思われる `<3>` は 1 回だけでした
- SIB16 に関係する文字列は見つかりませんでした。`ERRC_EVENT_SIB_INFO:SUBMITTED` (報知情報の受信) は出ますが、どの SIB かは書かれていません
- NITZ の時刻は秒単位なので、トレースから受信の瞬間が分かっても、1 秒より細かい時刻にはなりません

## 内蔵 GNSS (2026-11-18、未完了)

マニュアル §5.1 にはありませんが、ファームウェアのコマンド一覧 (`AT+CLAC`) に Intel の位置情報コマンド (`AT+XLCS*`、`AT+XLSRSTOP`) と `AT+GTCFGNMEA`・`AT+CPOS`/`AT+CPOSR` があります。引数の意味は ModemManager の旧 XMM プラグインのコメント等によります。

| コマンド | 結果 |
|---|---|
| `AT+XLCSINIT=?` | `+XLCSINIT: (INITIALIZE GNSS)` |
| `AT+XLCSSWITCH?` | `+XLCSSWITCH : 1,1,0` |
| `AT+XLCSLSR=2,3,,,,,1,,,1,118,0` (SUPL なし・単独測位・1 秒間隔・NMEA) | `+XLCSLSR: request id 1`、以後 1 秒ごとに NMEA (GGA/GSA/GSV/RMC/VTG、GPS・GLONASS・QZSS・Galileo・BeiDou) が要求したポートにだけ届く |
| `AT+XLSRSTOP` | 出力が止まる |

- 屋内 (机の上) で 5 分間: SNR が出た衛星は 0 機、測位なし (GGA 品質 0、RMC `V`)。GSV の衛星は暦から計算した位置だけ
- 測位前の NMEA の時刻はシステム時刻より約 9 時間 46 分進んでいて、使えません
- ThinkPad P14s Gen 4 の PSREF には GPS/GNSS の記載がなく、GNSS のアンテナがつながっているかは分かりません。窓際や屋外でも SNR が出なければ、アンテナがないと判断します (未検証)
- 測位できても 1PPS はなく、時刻は AT の通知で届くだけです。通知の遅れとそのばらつきを測るまで、時刻源としての精度は分かりません

## Linux での AT ポート

- `iosm` ドライバは 7560 に対して `/dev/wwan0at0`・`/dev/wwan0at1` (AT)、`/dev/wwan0mbim0` (MBIM)、ネットワークインターフェース `wwan0` を作ります
- AT ポートは TTY ではなく WWAN の文字デバイスです
- AT 経路には割り込みのまとめがかかりません (`IRQ_ACC_BACKOFF_OFF`)。データ経路は約 1 ms まとめられます (`IRQ_ACC_BACKOFF_MUX`)
- ModemManager は AT ポートを使うため、ltentp 用に 1 本外す必要があります (`contrib/udev/`)。実機では ModemManager を入れずに使っています
